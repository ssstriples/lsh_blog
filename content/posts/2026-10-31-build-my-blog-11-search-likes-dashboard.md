## 1. 검색 — "어디가 걸렸는지" 보여주기

검색 자체는 간단합니다. Prisma에서 이렇게 쓰면

```ts
{ title: { contains: q, mode: "insensitive" } }
```

PostgreSQL의 `ILIKE '%검색어%'`(대소문자 무시 부분 일치)로 바뀝니다.

> 💡 **ILIKE**: SQL의 `LIKE`에 "대소문자 구분 안 함(Insensitive)"이 붙은 PostgreSQL 연산자입니다.
> `%`는 "아무 글자나 몇 개든"이라는 뜻이라 `'%next%'`는 "next가 들어간 모든 것"을 찾습니다.

신경 쓴 건 결과 화면입니다. 제목만 보여주면 본문의 어디서 걸렸는지 알 수 없죠. 그래서 서버가
본문에서 **검색어 앞뒤 60글자만 잘라서**(`excerpt`) 내려주고, 화면에서 일치하는 부분을 노란색으로
칠했습니다.

```
Next.js 16 캐시 전략 정리
ISR [revalidate] 옵션으로 정적 페이지를 주기적으로 갱신합니다. 캐시 무효화는 [revalidate]Path로 합니다.
```

본문 전체(HTML)를 보내지 않으니 응답도 가볍습니다. 하이라이트도 HTML을 직접 끼워 넣지 않고, 문자열을
검색어 기준으로 잘라 "일치하는 조각만 `<mark>`로 감싸는" 방식이라 검색어에 `<script>`를 넣어도 안전합니다.

## 2. 로그인 없는 좋아요 — 쿠키로 "같은 사람" 알아보기

좋아요는 로그인 없이도 누를 수 있게 하고 싶었습니다. 그런데 **로그인을 안 했으면, 같은 사람이 두 번
누른 건지 어떻게 알까요?**

답은 **쿠키**입니다. 처음 좋아요를 누르면 서버가 랜덤 ID를 만들어 브라우저에 쿠키로 심어둡니다.
다음부터는 그 쿠키로 "아, 아까 그 사람이구나"를 압니다.

> 💡 **쿠키**: 서버가 브라우저에 맡겨두는 작은 메모입니다. 브라우저는 같은 서버에 요청할 때마다
> 이 메모를 자동으로 같이 보냅니다.

```ts
res.cookie("guestId", crypto.randomUUID(), {
  httpOnly: true,       // 자바스크립트로는 못 읽게 (훔쳐가기 어렵게)
  sameSite: "lax",
  path: "/api/posts",   // 좋아요 요청에만 실려 가도록
  maxAge: 365일,
});
```

몇 가지 원칙을 지켰습니다.

- **ID는 서버가 만든다.** 브라우저가 보낸 값이 정해진 형식(UUID)이 아니면 무시하고 새로 발급합니다.
  아무 문자열이나 넣어서 남의 좋아요를 흉내 낼 수 없게요.
- **로그인 유저는 계정으로** 셉니다. 그래야 휴대폰과 PC에서 각각 누르는 일이 없죠.
- 프론트(3000번 포트)에서 백엔드(4100번 포트)로 요청할 땐 `credentials: "include"`를 붙여야 쿠키가
  함께 갑니다. 이걸 빼먹으면 매번 "처음 온 사람"이 됩니다.

### 숨어 있던 DB 함정: NULL은 NULL과 다르다

DB에는 이미 "한 사람은 한 글에 좋아요 1번" 규칙(unique 제약)이 걸려 있었습니다.

```prisma
@@unique([postId, userId])
```

그런데 게스트는 `userId`가 비어 있습니다(NULL). 그리고 PostgreSQL에서 **NULL은 다른 NULL과 "같지 않다"**고
취급되기 때문에, 이 규칙은 게스트의 중복 좋아요를 전혀 막지 못합니다. 그래서 게스트용 규칙을 하나 더 걸었습니다.

```prisma
@@unique([postId, guestId])
```

화면에서는 버튼을 누르는 **즉시** 하트를 채우고 숫자를 올립니다(낙관적 업데이트). 서버 응답이 오면 실제
값으로 맞추고, 실패하면 원래대로 되돌립니다. 기다리는 느낌이 전혀 없죠.

> 솔직한 한계: 게스트는 쿠키를 지우면 또 누를 수 있습니다. 이건 막을 방법이 없어서, 1분에 30번까지만
> 누를 수 있게 속도 제한을 걸어 숫자 부풀리기를 늦추는 정도로 타협했습니다.

## 3. 대시보드 — 숫자 두 개가 서로 안 맞았던 이유

관리자 대시보드에는 총 회원·게시글·조회수·댓글과, **최근 14일 동안의 일별 조회수 차트**를 넣었습니다.

일별 조회수는 어디서 셀까요? 게시글의 `viewCount`는 누적 숫자라 날짜별로 나눌 수가 없습니다. 대신 5편에서
"같은 사람이 새로고침해도 조회수가 안 오르게" 만들어둔 **조회 기록 테이블**(`post_views`, 첫 조회 시각 포함)을
날짜별로 세면 됩니다.

그런데 첫 테스트 결과를 읽어보니 이상했습니다.

```
총 조회수: 1
오늘 조회수: 2   ← 오늘 하루가 전체보다 많다고?
```

원인은 **삭제된 글**이었습니다. 총 조회수는 "삭제되지 않은 글"의 조회수만 더했는데, 일별 집계는 조회 기록을
그대로 세서 예전에 지운 글의 기록까지 들어가 있었던 거죠. 두 숫자의 **기준이 달랐던** 겁니다.

```sql
FROM "post_views" pv
JOIN "posts" p ON p."id" = pv."postId"
WHERE p."deletedAt" IS NULL   -- 삭제된 글은 빼고
```

같은 이유로 "최근 댓글" 위젯에도 지운 글의 댓글이 떠 있었습니다(누르면 404). "보이는 댓글"의 조건을 한 곳에
상수로 모아두고 대시보드와 관리자 댓글 목록 모두 같은 조건을 쓰게 했습니다.

> 💡 **교훈**: 테스트가 "통과"해도 숫자가 맞는 건 아닙니다. 이후엔 "14일 합계는 전체 조회수보다 클 수 없다"는
> **숫자 사이의 관계** 자체를 테스트로 만들었습니다.

그 밖의 디테일 두 가지:

- **시간대**: DB는 시간을 UTC(영국 기준)로 저장합니다. 그대로 날짜를 자르면 한국 기준 오전 9시에 날짜가 바뀌죠.
  그래서 한국 시간으로 바꾼 뒤 날짜를 나눴습니다.
- **조회가 없는 날은 0으로 채웁니다.** 빠진 날이 있으면 차트의 간격이 들쭉날쭉해집니다.

## 4. 차트를 "규칙대로" 그리기

차트는 Recharts로 그렸는데, "보기 좋게"를 감으로 하지 않으려고 정해진 절차를 따랐습니다.

1. **차트가 맞나?** — 총계 4개는 차트가 아니라 큰 숫자 카드면 충분합니다. 차트는 "14일 추이" 하나만.
2. **색은 하나.** — 선이 하나뿐이니 범례 상자도 필요 없습니다. 제목("일별 조회수 (최근 14일)")이 설명하니까요.
3. **색을 "계산"으로 검증** — 파란색이 실제 배경(라이트: 흰색, 다크: 거의 검정) 위에서 충분히 보이는지
   대비를 스크립트로 확인했습니다. 라이트/다크 각각 다른 파란색을 씁니다.
4. **얇고 조용하게** — 선 2px, 아래 면은 10% 투명도, 격자는 아주 연한 실선. 데이터만 눈에 띄게.
5. **마우스를 올리면** — 세로선이 가장 가까운 날짜에 붙고, 툴팁에는 **숫자가 크게 먼저**, 날짜는 작게.
6. **표로 보기** — 마우스 없이도(키보드, 화면 낭독기) 모든 값을 볼 수 있게 표를 함께 둡니다.
7. **그리고 눈으로 본다** — 스크린샷을 찍어보니 부드러운 곡선(`monotone`)이 날짜 사이를 이어서 **있지도 않은
   중간값**이 있는 것처럼 보였습니다. 하루 단위 숫자에는 직선이 정직합니다. `linear`로 바꿨습니다.

## 5. 정지된 계정이 15분 동안 글을 쓸 수 있었다

관리자가 스팸 회원을 **정지**할 수 있게 했습니다. 그리고 "정말 막히나?"를 경로별로 점검해봤습니다.

| 경로 | 정지 계정 |
|---|---|
| 로그인 | 막힘 ✅ |
| 토큰 재발급 | 막힘 ✅ |
| 댓글 작성 | 막힘 ✅ (10편에서 처리) |
| **글쓰기·수정·삭제** | **안 막힘 ❌** |

왜일까요? 4편에서 만든 로그인 토큰(Access Token)은 **15분 동안 유효**합니다. 그리고 서버는 글쓰기 요청이 오면
"토큰이 진짜인가"만 확인하지, "이 사람이 **지금도** 정상 회원인가"는 확인하지 않았습니다. 토큰에 적힌 정보는
**발급받은 순간의 정보**니까요. 그래서 정지 직후 15분 동안은 남은 토큰으로 글을 쓸 수 있었습니다.

글쓰기 같은 **쓰기 요청에만** "지금 상태를 DB에서 다시 확인하는" 관문을 하나 추가했습니다.

```ts
router.post("/", requireAuth, requireActiveUser, create);
//                            ^^^^^^^^^^^^^^^^^ 정지됐으면 403
```

모든 요청에 붙이면 글 읽기까지 느려지니, 쓰기에만 붙였습니다. 테스트로 "정지 직후, 아직 살아있는 토큰으로
글쓰기 → 403"을 확인했습니다.

그 밖에 지킨 규칙:

- 관리자는 **자기 자신**과 **다른 관리자**를 정지할 수 없습니다 (실수로 관리자가 사라지는 사고 방지).
- 요청에 `role: "ADMIN"`을 슬쩍 끼워 넣어도 무시됩니다 (입력 검증 스키마에 그 필드가 아예 없어요).
- 누가 누구를 정지했는지 보안 로그를 남깁니다.

## 6. 트러블슈팅: 브라우저를 띄워봐야 보이는 에러

이번엔 처음으로 실제 브라우저(Chrome)를 자동으로 띄워 화면을 찍어봤습니다. 그런데 스크린샷 구석에
Next.js 개발 도구가 **"2 Issues"**라고 빨갛게 표시하고 있었습니다. 서버 로그는 깨끗했는데 말이죠.

브라우저 콘솔을 수집해보니 모든 페이지에서 같은 에러가 나고 있었습니다.

```
Base UI: A component that acts as a button expected a native <button> ...
Use a real <button> in the `render` prop, or set `nativeButton` to `false`.
```

> 💡 버튼 모양의 **링크**를 만들 때, 버튼 컴포넌트에 "실제로는 링크로 그려줘"라고 시키는 방법이 있습니다.
> 그런데 이 UI 라이브러리는 "진짜 버튼이 아니라면 그렇다고 알려달라"(`nativeButton={false}`)고 요구합니다.
> 그래야 화면 낭독기 같은 보조 기술이 이걸 버튼이 아니라 링크로 제대로 안내할 수 있거든요.

헤더의 "글쓰기", "로그인" 버튼은 **6편부터 계속** 이 상태였습니다. 그동안 HTTP 응답 코드와 HTML만 확인하는
테스트로는 전혀 보이지 않던 문제였죠. 7곳에 한 줄씩 추가하고 다시 확인하니 에러 0건이 됐습니다.

> 💡 **교훈**: "페이지가 200으로 응답한다"와 "브라우저에서 문제없이 돈다"는 다릅니다.

## 마무리

이번 편의 핵심을 정리하면,

- 좋아요의 "같은 사람"은 **서버가 발급한 쿠키**로, 로그인 유저는 계정으로
- DB에서 **NULL은 NULL과 같지 않다** — 게스트용 중복 방지 규칙이 따로 필요했다
- 숫자는 **기준을 통일**해야 서로 맞는다
- 권한은 **토큰이 아니라 지금 상태**로 판단해야 할 때가 있다
- 차트도 화면도 **직접 렌더링해서 눈으로** 확인한다

다음 편에서는 AI를 활용한 글쓰기 파이프라인을 다룹니다. 요구사항 명세서와 기술 명세서를 만들어주는
프롬프트 템플릿을 다듬고, 관리자 글쓰기 화면에 "AI 초안 생성" 버튼을 붙여볼 예정입니다.
